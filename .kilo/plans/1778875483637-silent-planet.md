# Pedigree PRO — Comprehensive Codebase Audit & Action Plan

## 1. Project Overview

**Pedigree PRO** is a zero-server clinical pedigree (family tree) editor for genetic counselors and clinicians. It runs entirely locally — either as a Tauri desktop application (Rust + SQLCipher backend) or as a browser standalone (sql.js WASM + IndexedDB + Web Crypto API). No cloud, no REST API, no internet required.

### Architecture

```
┌──────────────────────────────────────────────────┐
│            Frontend (React + Vite + Tailwind)     │
│            @workspace/haplopainter                │
│  Pages: Dashboard, Patients, Pedigrees, Profiles  │
│  Canvas: SVG-based pedigree drawing engine        │
│  State: React Query + component-local useState    │
└──────────────┬────────────────────────────────────┘
               │ @workspace/api-client-react
               │ (adapter detects runtime mode)
       ┌───────┴────────┐
       ▼                ▼
┌──────────────┐  ┌───────────────────┐
│  Tauri IPC   │  │  @workspace/     │
│  invoke()    │  │  browser-backend │
│              │  │  (sql.js WASM)   │
└──────┬───────┘  └───────┬───────────┘
       ▼                   ▼
┌──────────────┐  ┌───────────────────┐
│  Rust Backend│  │  IndexedDB +      │
│  SQLCipher   │  │  Web Crypto API   │
│  OS Keychain │  │  @workspace/crypto│
└──────────────┘  └───────────────────┘
```

## 3. Architectural Observations

### 3.1 Strengths

1. **Local-first architecture is well-designed.** The dual-backend adapter pattern (Tauri IPC vs. browser sql.js) is clean and minimal (~77 lines in `adapter.ts`). Snake_case command names provide a uniform interface.

2. **HIPAA-compliant by design.** Self-hosted fonts, Ed25519 signing, SHA-256 content hashing, SQLCipher + AES-GCM encryption at rest, no telemetry, no cloud dependency. ADR-001 through ADR-004 and COMPLIANCE-HIPAA.md provide thorough documentation.

3. **SVG-based pedigree canvas avoids heavy dependencies.** No D3, no React Flow. Pure React SVG rendering with `React.memo` optimization on NodeShape and EdgeLine.

4. **React Query for all server state.** Cons caching, cache invalidation, and stale-while-revalidate patterns. 27 hooks with structured query keys.

5. **The monorepo structure is well-organized.** Clear separation: `lib/crypto` (primitives), `lib/db` (schema + migrations), `lib/browser-backend` (CRUD + DB management), `lib/api-client-react` (adapter + hooks), `artifacts/haplopainter` (UI).

### 3.2 Technical Debt

1. **No state management for canvas.** `pedigree-canvas.tsx` has ~40 `useState` calls. This is a maintenance risk. A state machine (XState) or reducer pattern would improve traceability and testability. The component is ~525 lines and growing.

2. **11 `any` types in `lib/db/src/index.ts`.** All table exports and the `db`/`pool` variables are typed as `any` due to conditional SQLite/Postgres loading. This erodes type safety for all DB-consuming code.

3. **Deprecated function aliases in `@workspace/crypto`.** `sealData`, `unsealData`, `sealForRecipient`, `unsealFromSender` are still exported. Should be removed or at minimum marked with `@ts-deprecated` to surface in IDEs.

4. **Dead code: `custom-fetch.ts`** (371 lines). Legacy HTTP fetch client from the removed API server. Not imported anywhere. Should be deleted.

5. **Legacy `init-sqlite.js` and `init-sqlite.cjs`** scripts use the pre-ADR-002 schema without crypto columns or `local_profiles`. Only `init-sqlite-async.mjs` has the correct schema.

6. **Inconsistent naming.** Internal draft keys use `haplopainter_draft_*`; CSS variables and localStorage keys mix `hiblopainter` and `pedigree-pro` prefixes. Package name remains `@workspace/haplopainter`.

7. **`canvas-theme.ts` was deleted** but some references may still exist. All theming should consistently use `hsl(var(--primary))`.

8. **SQLCipher** in the browser-backend is actually AES-GCM application-layer encryption (not SQLCipher). The naming in `crypto-store.ts` and `db.ts` (key `sqlcipher-data`) is misleading since SQLCipher is only available in the Tauri/Rust path.

### 3.3 Security Concerns

1. **`encryptForRecipient` uses SHA-256 key wrapping — NOT real public-key encryption.** This is marked `@deprecated` with a WARNING but is still the *active* code path for `share_pedigree()`. An attacker with the recipient's public key could derive the shared secret because SHA-256(publicKey) is deterministic. This violates the ADR-001 trust model. **Remediation: Replace with libsodium sealed box (`sodiumSealBox` is already implemented but unused in sharing).**

2. **`Uint8Array as unknown as ArrayBuffer` double-casts** in `crypto-store.ts` (7 instances). While Web Crypto accepts `BufferSource`, the cast is misleading. Use `.buffer` property for proper `ArrayBuffer` extraction.

3. **No input validation on `import_pedigree_native`** in browser-backend. The `path` parameter is treated as JSON content, parsed with `JSON.parse()`, and inserted into SQL without parameterized queries in some paths. While `exec()` uses parameterized queries, the JSON parsing itself could fail with malformed input.

4. **`beforeunload` data loss risk.** `saveDb()` is async but `beforeunload` doesn't wait for promises. A `navigator.sendBeacon()` fallback or synchronous XHR is needed.

5. **No FK enforcement in SQLite.** `PRAGMA foreign_keys = ON` is not set. Cascading deletes and FK constraints in migrations are inert.

6. **SQLite schema missing `.unique()` on `users.email`** (Postgres has it). While `users` is deprecated, the inconsistency suggests schema drift between Postgres and SQLite variants.

7. **Private key storage in IndexedDB** is correct (per AGENTS.md — no `localStorage` for key material), but IndexedDB is still accessible to XSS. The Tauri mode uses OS keychain which is more secure. Browser mode should at minimum encrypt private keys before storage.

### 3.4 Scalability Limitations

1. **Singleton DB in browser mode.** `db.ts` uses module-level `let db: SqlJsDatabase | null = null`. No connection pooling, no concurrent access patterns, no IndexedDB transaction queuing.

2. **30-second auto-save interval is not configurable.** High-frequency editors may lose up to 30 seconds of data.

3. **No Web Worker for DB operations.** All sql.js operations run on the main thread. Large pedigrees (100+ nodes) may block the UI during save/query.

4. **Version history is unbounded.** No pruning or archival strategy for `pedigree_versions`.

5. **No offline sync or conflict resolution.** The LAN sharing model assumes one writer at a time with manual merge via `ImportReviewModal`.

## 6. Summary

The Pedigree PRO codebase demonstrates strong architectural foundations: local-first design, HIPAA-compliant encryption, zero-cloud-dependency, and a clean dual-backend adapter pattern. The SVG pedigree canvas is well-implemented with comprehensive interaction support.

**The single most critical issue** is P0-1: `encryptForRecipient` uses deterministic SHA-256 key wrapping instead of proper public-key encryption, which violates the project's own ADR-001 trust model. This must be replaced with `sodiumSealBox` before any sharing feature is considered production-safe. This is also a prerequisite for P1-7 (.ppro file export/import).

**The most impactful architectural debt** is P2-1: the 40+ `useState` calls in `pedigree-canvas.tsx`. This is the most complex component in the app and it will become increasingly difficult to maintain and test without a state machine or reducer pattern.

**The most impactful testing gap** is P1-4: zero tests for `@workspace/browser-backend`, which is the entire data layer in browser mode. A bug in `commands.ts` or `db.ts` could silently corrupt clinical data.

**The CI pipeline has a broken job** (P0-3) referencing the deleted `services/relay/` directory, which will cause `deploy-relay` to fail on every main push.

### Key Decisions Made

- **Profile Export/Import**: Not needed. Clinician sharing is via .ppro file exchange, not full DB backup.
- **Schema Migration**: No production data exists → deprecated columns can be dropped in a single migration (no dual-write).
- **On-Premises Server**: Not needed. Contradicts local-first architecture. Permanently removed.
- **Profile Switcher**: Not needed. One device per clinician = identity setup, not switching.
- **DB Management**: backup/restore/rotate_key stubs → replaced with .ppro file export/import (Option A first, then relay Option B).
